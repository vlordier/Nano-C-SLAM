# Stale-odometry Gazebo diagnostic (incomplete; do not accept as pass)

This first live stale-odometry attempt verified that the launch can isolate the `/cf1/odom` bridge: after the mission reached HOVER, the probe sent SIGINT only to session-owned bridge PID 17773, while `/clock`, the general control bridge, controller, and independent read-only truth odometry continued. SimMission then published matching `FAILED` with reason `odometry data is stale`, exited 1, and emitted 13 zero `cmd_vel` commands. The separate Gazebo truth stream supplied 250 samples over 5.002 seconds after mission exit; altitude was 0.759803–0.760433 m and maximum absolute vertical velocity was 0.000222 m/s.

Adversarial review found one `enable=True` received 28 microseconds after the `FAILED` status timestamp. Because the probe used separate ROS topics and cannot establish cross-topic publisher ordering at that boundary, this attempt is conservatively marked **failed/inconclusive for the no-enable-after-failure criterion**. It exposed a mission-timer ordering defect: `_step` published enable before calling the state machine, which could fail for stale odometry in that same tick. The code now evaluates the state transition before arming, and the probe asserts zero enable events after FAILED. This trial is retained only as diagnostic evidence; see a later attempt for the rerun.

The source checkout was dirty during this run. Its overlay receipt/snapshot, raw JSON, logs, plugin hash, world session manifest, command, and process teardown audit are retained for diagnosis. The GUI required SIGKILL after SIGINT/SIGTERM, another limitation recorded for follow-up. This is Gazebo-only evidence and makes no hardware-safety claim.
